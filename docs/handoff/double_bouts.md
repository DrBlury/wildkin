# Paired route wardens: real doubles are not yet implemented

**Status:** Blocked on a four-battler combat/renderer redesign. The current game still starts two *independent 1v1 bouts* when two wardens challenge the player; no route currently satisfies the §8 requirement for an actual double bout. Do not call a combined sequential trainer team, two back-to-back battles, or two trainer sprites alongside one active enemy a double bout. No gameplay files were changed by this handoff.

## Evidence and scope

- `docs/plans/01_progression_contract.md` §5, “Warden density on a new route,” requires at least one double per new two-segment route; §8 item 4 repeats the double-bout route checklist. Plans 03–07 expressly name twins, reed-cutters, spa-goers, dream twins, climbers, and pilgrims; plan 08 mentions paired rangers but does not specify doubles for its loops.
- `src/game/battle.c`: `battle.ally` and `battle.team_idx` are singular active slots; `side_mon(side)` maps each side to exactly one kin. `stages[2]`, `flinch[2]`, and `disp[2]` each have only one instance per side. `battle_take_turn()` schedules two actions using `!first`; `enemy_only_turn()` schedules one. `finish_turn()` tests just one foe and one ally; `queue_enemy_fainted()` sends out the next *single* reserve and pays one trainer prize at the end. `BEvent.side` identifies a side, not a particular target. Existing traits, status, switching, XP, bag actions, and forced switches all depend on these assumptions.
- `src/game/battle_ui.c`: `battle_reset()` chooses one ally; `battle_queue_intro()` sends one foe and one ally. `battle_load_mon_gfx()` loads one graphic per side. `battle_draw_battlers()` loops over two sides and selects `OT_MON_A/B` and `OBANK_MON_A/B`; HUD/event processing likewise indexes a single display per side. `src/game/anim.c` uses `!anim.side` for the target in move effects, so extending combat alone would animate hits on the wrong kin. Additional simultaneous monster tiles/palettes and visible HP/status HUDs need a budgeted graphics/UI layout; merely drawing a second sprite with the same tile shows the first species twice.
- `src/game/script.c`: `check_spotting()` picks the first eligible warden, `spot` holds one NPC, and `script_warden()` calls `warden_battle()` for one `TrainerDef`. The end hook stores one `warden_battling` trainer ID and marks one bit only on `BR_WIN`. `src/game/field.c` has persistent `trainer_bits` for both trainer IDs and per-NPC map visibility, but `NpcDef`/`TrainerDef` has no pair binding. `battle_exit()` invokes the hook once after resolving loss/return; a coordinated outcome must mark both IDs atomically on victory only. It must pay both existing prizes once, with no overflow/duplicate rewards, and retain the bits' save layout.
- Existing paired names do not imply proximity: Oak/Ash are at `(26,16)`/`(39,15)` in `world/east/npcs.inc`; Bo/Eli at `(13,27)`/`(24,26)` in `world/north/npcs.inc`. Even the closest pilgrims at `(28,16)`/`(29,16)` in `world/grim/npcs.inc` will not pair under the current first-seen scan. Distance-only grouping would accidentally pair unrelated wardens and miss named pairs. Region-placement changes require coordination with the region owners and are outside this worktree's ownership.

## Implementation strategy for a real 2v2 (separate, coordinated change)

1. **Define explicit pair identity and eligibility.** Add a deliberate trainer-ID pair registry for the named route pairs (and opt-in loop rangers only if their owners confirm intent), *not* a nearest-NPC heuristic. Resolve both NPCs on the same map, visible and undefeated, and reachable from the player's encounter tile at the same elevation. Either warden's talk or sight trigger should choose one deterministic pair and reserve both NPCs so the second cannot enqueue its own encounter. A previously defeated solo member or an absent/hidden partner must fall back to the normal solo warden; do not force a rematch or block the route. Do not alter persisted `NpcDef`/save structures just to hold temporary encounter state.
2. **Model four active combatants.** Introduce two active ally party slots and one active kin slot per trainer, with trainer ownership for reserves, stages, flinch, entry traits, participation, and HP/status. Require at least two healthy ally kin before triggering a double, otherwise explicitly fall back to a solo warden (or design a documented one-ally handicap and test it). Resolve four queued choices by priority/speed/tie-break, skip fainted actors, select an explicit surviving target for each enemy-facing move, and define self/ally/AoE semantics for every move. If the selected target faints first, retarget to a live foe or skip safely; never alias a fainted target. Forced substitutions, opponent reserve selection, recoil/double KOs, end-of-turn effects and item/switch actions each need per-slot behavior. Keep the 1v1 path and its event order unchanged.
3. **Render and animate four independent kin.** Reserve distinct graphics tiles/palettes for all four monster species without overwriting OAM, UI, portrait, or FX budgets; provide two HUDs per team with HP/status and unambiguous target cursor(s). Carry both side and active slot/target in animation and event records, update `src/game/anim.c` and any graphics loader/VRAM layout as required, and verify hits and fades are attached to the correct kin. This exceeds the four-file bounded battle/warden initiation scope; no fake second sprite is acceptable.
4. **Settle both wardens exactly once.** Use a distinct `battle_start_trainer_pair()` that retains each trainer's team, ID, portrait/name, and prize. Award XP once per fainted kin and each trainer's prize once on a final `BR_WIN`; preserve bonus/meal semantics across one battle. On `BR_LOSE`, leave both trainer bits unset; on win, mark exactly the two pending IDs in the existing `trainer_bits` via the single end hook. Clear pending pair state before returning to the field, and ensure completed pairs' dialogue, spotting, save/reload, and solo fallback remain usable.
5. **Coordinate map placement and rollout.** Confirm where the paired sight or talk trigger can meet both partners on each route before changing region NPC coordinates. First land a four-slot battle core and UI/animation with a synthetic host fixture; then enable one actual route pair and validate in emulator; finally opt in the other named pairs with map-owner review. Do not merge merely because two sequential trainer fights pass.

## Acceptance checks for the later implementation

In `tools/tests/test_double_bout.c` (the Makefile automatically picks up `tools/tests/test_*.c`): verify start from either trainer and sight/talk, two independently visible foes and allies, target selection/retargeting, four-action speed/priority order, per-slot status/traits, switch/item turns, PP, faint and reserve replenishment, double KO and two-versus-one cleanup, no healthy second ally, partial previously defeated pairs, and no battle-entry duplication. Verify XP, both prizes exactly once, both trainer bits only after win (including save/reload), no bits on loss, both NPCs' dialogue after win, and no softlock after a loss. Preserve the existing 1v1 `tools/tests/test_battle.c` coverage. Run `make test`, `make` with the GBA toolchain, and a real narrow-screen battle capture showing four distinct sprites, HP bars, targeting, and faint replacement without tile/palette corruption.

This handoff is an explicit blocker, not a claim that the doubles acceptance criteria have passed. No new double-bout host test is added yet: without a four-active API it could only test existing 1v1 behavior or encode a knowingly false double.
